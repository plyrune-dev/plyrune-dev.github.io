Planned · not released

Source to change, without losing the thread.

Plyrune (pronounced “PLY-roon”) is a planned engineering toolkit. It gives a coding agent one interface for finding source, keeping exact captures, inspecting bounded views, preparing candidate edits and checking declared obligations.

Nothing is released yet. This page sets out the design and says plainly what is available, what is only planned and what has not been measured. It is not a running Plyrune engine.

The proposed flow

Design vocabulary, not an API

  1. 1 Query

    Every exact match, in a scope you declare.

    selection · complete for that scope

  2. 2 Inspect optional

    A bounded view of a few captures.

    view · the selection stays whole

  3. 3 Prepare

    An exact candidate, built from the captured bytes.

    candidate · not applied

  4. 4 Check

    Coverage of a requirement that was admitted independently of the matches.

    report · bound to that candidate

Candidate only. None of these four steps writes to your working tree.

– Apply to a working tree

Not part of milestones M1–M4. A separate host protocol, optional and later.

Names such as selection and report are proposed artifact types. No such operation exists yet.

Shared captures. Explicit scope. Reusable evidence.

One interface · retained identity

Inspect a little. Keep the whole selection.

A query returns a complete selection for the scope you declared. Inspection is optional and bounded: showing two captures leaves all six available to the proposed edit and to the coverage check. Displaying less never means selecting less.

Proposed operationsIllustrative, not runnable
selection = query(snapshot, requirement)
view      = inspect(selection, limit=2)
candidate = prepare(selection, replacement)
report    = check(requirement, candidate)

// The view does not replace the selection.

In the proposed design, a harness whose replacement is fully specified could run these steps as one script, with no model turn in between. A judgement that depends on what the model sees would resume later with the retained handles.

Not measured yet: what will be counted

The first composition claim, as it is proposed to be stated

Given the identified immutable inputs and validated operations, the candidate uses the selected source bytes, preserves untouched bytes, and the coverage report refers to that exact candidate and independently admitted requirement.

Status: planned. It has not been proved for Plyrune. Any future claim will name the exact functions, revision, translation and assumptions it depends on.

  1. PR-C01

    Admitted capture resolves the named resource and snapshot range with exact bytes.

    Planned negative control: omit the owner or snapshot comparison.

  2. PR-C02

    Complete literal selection equals every supported match and carries a complete declared-inventory witness.

    Planned negative control: skip a matching resource; separately omit a required no-match inventory witness.

  3. PR-C03

    Lowering retains target and source identity and range.

    Planned negative control: swap equal-looking captures across owners.

  4. PR-C04

    Candidate changes exactly the admitted targets, preserving untouched bytes.

    Planned negative control: drop an untouched gap or file.

  5. PR-C05

    Accepted coverage answers the independently admitted requirement.

    Planned negative control: bind the requirement to only the returned matches.

  6. PR-C06

    Report refers to the exact candidate, requirement, premises and checker profile.

    Planned negative control: substitute a different candidate or requirement.

  7. PR-C07

    Each supported operator preserves sufficient dependencies.

    Planned negative control: drop the right operand of a difference, or a no-match resource dependency.

  8. PR-C08

    Composition preserves PR-C01 to PR-C07 under named premises.

    Planned negative control: break an interface binding.

Inherited evidence keeps its own scope

Plyrune reran Splicery’s native proof gate on its pinned source. Weft’s proofs remain upstream results. Neither establishes that Plyrune lowers a selection to the right edits or checks the resulting candidate against the original requirement.

Roadmap · status on 24 November 2026

Prove the small path. Then earn the larger one.

These are scope and acceptance boundaries, not calendar promises. Each step has to show its evidence before the next one is trusted.

  1. M0In progress

    Contracts and baseline

    Six native reference tasks now have reproducible traces. The source inventory and requirement framing are still open.

  2. M1Not started

    Pure composition

    Immutable input, a literal selection, an exact candidate and a coverage report, with no workspace writes.

  3. M2Not started

    Agent interface

    One command-line and stdio surface with retained handles and bounded inspection, plus an early cost comparison.

  4. M3Not started

    Revalidation

    Sound, conservative reuse and an immutable refresh. Clever incrementality waits until traces show it is worth having.

  5. M4Not started

    Controlled evaluation

    A reproducible paired study with independent grading, complete records and negative results.

  6. M5Optional

    Live application

    One qualified adapter for applying a candidate, only if a concrete adopter needs it.

Evaluation · proposed method

A fair test against the tools agents already use.

The question is not whether a kernel is fast or an answer is short. It is whether sharing exact artifacts helps a complete task, compared with competent ordinary tooling.

  1. A
    Native tools

    The harness’s own read, search and patch commands, plus shell or code-mode scripting and batching. This is the baseline to beat.

  2. B
    Unified facade

    The same operations with ordinary text handoffs. Isolates the benefit of a single interface.

  3. C
    Shared artifacts

    Retained exact captures, views and candidate and report identities. Isolates the benefit of composing artifacts.

  4. D
    Incremental reuse

    Arm C plus admitted dependency-aware reuse, measured after M3.

Every arm can script and batch. The grader does not call the tool under test. Failures stay in the denominators, cold and warm runs are reported separately, and no arm is weakened to produce a win.

An early paired pilot is a go/no-go checkpoint, not a marketing study. If success is at ceiling and the interface costs more, the intended use case narrows or the interface gets simpler.
